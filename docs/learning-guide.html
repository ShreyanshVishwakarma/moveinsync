1. What the application does

This project is a configuration server for a ride-management system. It does not book rides. It stores settings, validates them, records their history, and pushes updates to connected services.

Configuration definitionsDescribe a setting, its type, default value, and validation rules.
OverridesCustomize a setting for a client, office, or shift.
Change setsPublish one or more changes as a single numbered version.
Live propagationPush new versions to connected clients through WebSockets.

Configuration has four levels:

GLOBAL
  └── CLIENT
        └── OFFICE
              └── SHIFT

The most specific value wins:

SHIFT → OFFICE → CLIENT → GLOBAL default
LevelExample value
GLOBAL60 minutes
CLIENT acme-corp45 minutes
OFFICE blr-office-130 minutes
SHIFT night20 minutes

A request for the night shift receives 20 minutes.

2. How a request moves through the app

Reading a configuration

HTTP request
    ↓
Controller
    ↓
Service
    ↓
In-memory ConfigSnapshot
    ↓
HTTP response

Writing a configuration

HTTP request
    ↓
Controller
    ↓
ConfigChangeService
    ↓
Validate every value
    ↓
Save the change set in one database transaction
    ↓
Build a new immutable snapshot
    ↓
Publish the snapshot atomically
    ↓
Broadcast an update over WebSocket
    ↓
HTTP response
Important: normal reads use the in-memory snapshot instead of querying the database. This makes reads fast and prevents a reader from seeing half of a multi-key update.

7. Repository classes

Repositories are the database access layer. Spring Data JPA creates their implementations automatically.

FilePurpose

ConfigOverrideRepository.javaFinds and saves scoped configuration overrides.
ChangeSetRepository.javaFinds versions, including the latest version.
ChangeSetEntryRepository.javaLoads audit entries for synchronization and rollback.

8. Snapshot classes

FilePurpose
snapshot/ConfigSnapshot.javaImmutable, indexed view of definitions and overrides. Resolves values quickly.
snapshot/SnapshotStore.javaStores the current snapshot in an AtomicReference and replaces it atomically.
service/SnapshotLoader.javaLoads database data and builds a new snapshot.
service/SnapshotBootstrap.javaLoads the initial snapshot during application startup.
Why this matters: a reader sees either the complete old state or the complete new state, never a mixture of both.

ConfigChangeService.java is the key write-path file

Receive change set
  → Acquire CommitGate
  → Validate every entry
  → Begin database transaction
  → Create change_set row
  → Update config_overrides
  → Create audit entries
  → Commit transaction
  → Build and publish a new snapshot
  → Publish a WebSocket event

16. Running the application

Requirement: Java 21.

# Linux, macOS, or Git Bash
./mvnw spring-boot:run

# Windows Command Prompt or PowerShell
mvnw.cmd spring-boot:run

Run tests:

# Linux, macOS, or Git Bash
./mvnw test

# Windows
mvnw.cmd test

Useful URLs:

  • http://localhost:8080/h2-console
  • http://localhost:8080/actuator/health
  • http://localhost:8080/actuator/prometheus
  • ws://localhost:8080/ws/config

17. Current limitations

  • Authentication is not implemented.
  • Role-based access control is not implemented.
  • Tenant isolation is not enforced yet.
  • The embedded client SDK is not implemented yet.
  • The default WebSocket origin setting is open for demo purposes.
  • Production database migrations should use Flyway or Liquibase.

Final mental model

Definitions describe settings.
Overrides customize settings for a client, office, or shift.
Change sets version changes.
Repositories read and write the database.
Services implement the business rules.
Snapshots make reads fast and atomic.
Controllers expose REST APIs.
WebSockets push new versions to clients.
Tests verify the important behavior.
